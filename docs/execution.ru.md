# Выполнение команд, секреты и результаты

**Русский** | [English](execution.md)

---

Клиент использует системный OpenSSH.

Пользовательские команды выполняются на удалённом сервере через небольшой вспомогательный обработчик на Python 3.

Исходный код обработчика и случайный идентификатор сеанса передаются через аргументы командной строки (`argv`). Сама команда и связанные с ней секретные значения передаются в структурированном запросе через стандартный ввод SSH (`stdin`).

Максимальный размер запроса составляет **1 МиБ**.

Для самой команды действует отдельное ограничение в **32 КиБ UTF-8**, поскольку обработчик запускает её через `sh -c` или `bash -c`.

## Секреты

Не подставляйте значения параметров с `secret: true` непосредственно в текст команды. Вместо этого привязывайте секреты к конкретному шагу сценария.

Пример:

```yaml
id: secret-example
name: Secret input example
os: [unix]
shells: [sh]
parameters:
  token:
    secret: true
steps:
  - name: Read token
    secrets: [token]
    command: |
      python3 <<'PY'
      import os
      fd = int(os.environ['NODEBATCH_SECRET_token_FD'])
      token = os.read(fd, 4096).decode('utf-8')
      os.close(fd)
      # Use token in this process; do not pass it to subprocess argv.
      print('Token received')
      PY
```

Для каждого секрета создаётся отдельный анонимный канал передачи данных (`pipe`).

В переменные окружения помещается только номер файлового дескриптора, через который можно получить значение секрета.

Один шаг сценария может использовать до **32 секретов**, размер каждого из которых не должен превышать **4096 байт UTF-8**.

Для секретных параметров запрещены:

- Сохранённые значения по умолчанию.
- Символы перевода строки.
- Нулевые байты (`NUL`).

Известные значения секретов маскируются в выводе, в том числе когда их содержимое поступает несколькими отдельными блоками.

Однако преобразованные значения, например закодированные в Base64, не могут быть надёжно обнаружены и скрыты автоматически.

Python не гарантирует полное удаление секретных значений из оперативной памяти.

Доверенными компонентами по-прежнему считаются код, непосредственно получающий секрет, привилегированное программное обеспечение на удалённом сервере и процессы, имеющие эквивалентный доступ.

## Sudo и стандартный ввод

Фактически для привилегированного выполнения используется команда следующего вида:

```text
sudo -S -p <random prompt> -u <target user> -- python3 -u -c <helper source> <session>
```

Вспомогательный обработчик способен выполнять произвольные команды. Поэтому разрешение на его запуск фактически предоставляет возможность выполнять произвольный код от имени целевого пользователя.

Политика sudo, разрешающая исключительно `sh` или `bash`, не разрешает автоматически запуск такого обработчика.

NodeBatch не изменяет файл `sudoers` и не устанавливает зависимости на удалённые серверы.

Ограничительные политики sudo, параметр `requiretty` и нестандартные последовательности запросов PAM в общем случае не поддерживаются.

До получения сообщения `ready` стандартный ввод используется исключительно для передачи ответов на запросы пароля sudo.

Если настроен `NOPASSWD`, диалог ввода пароля не требуется. Во время авторизации допускаются повторные попытки.

После получения `ready` клиент передаёт один запрос и сигнал окончания ввода (`EOF`).

Запущенная пользовательская программа получает `/dev/null` в качестве стандартного ввода. Секреты передаются через отдельные файловые дескрипторы.

Поздно поступившие ответы на запросы пароля привязаны к исходному процессу и не могут попасть в следующий процесс.

На авторизацию распространяются тайм-ауты подключения и аутентификации.

Отсчёт времени выполнения начинается после получения `ready` и включает передачу запроса и подготовку запуска процесса.

## Протокол v2

Стандартный вывод SSH используется для передачи сообщений в формате JSONL.

Стандартные потоки вывода пользовательской программы (`stdout` и `stderr`) обрабатываются через отдельные каналы и передаются в виде кадров (`frames`) типа `data`.

Текст пользовательской программы никогда не интерпретируется как управляющее сообщение протокола.

Идентификатор сеанса связывает сообщение `ready` с конкретным вызовом.

Дополнительный случайный токен связывает все последующие сообщения с соответствующим запросом.

Протокол предусматривает следующие сообщения:

- `not_started` - подтверждает, что подготовка завершилась ошибкой до создания пользовательского процесса.
- `started` - подтверждает создание процесса. Это сообщение должно предшествовать выводу и результатам выполнения.
- `result` - подтверждает код завершения оболочки, включая значение `255`. Необязательный логический параметр `output_incomplete` указывает, что потоки были закрыты после достижения ограничения на сбор оставшегося вывода.
- `error` - если сообщение поступило после `started`, оно означает сбой обработчика без подтверждённого результата выполнения.

Некорректные сообщения, незавершённые терминальные сообщения, дубликаты и сообщения с нарушенным порядком не могут подтверждать успешное выполнение команды.

Если запрос не был отправлен, клиент достоверно знает, что пользовательская программа не запускалась.

После передачи запроса отсутствие подтверждения означает, что результат выполнения неизвестен.

SQLite отдельно сохраняет:

- Исходный код завершения SSH.
- Подтверждённый код завершения команды.
- Поле `command_started`, допускающее значение `NULL`.

Автоматический повтор выполнения не производится.

Отмена задания не позволяет гарантировать, что все дочерние и фоновые процессы на удалённом сервере завершились.

## Фоновые процессы

Результат выполнения относится к основному процессу `sh -c` или `bash -c`, а не к созданным им дочерним процессам.

Вспомогательный обработчик отслеживает завершение оболочки независимо от чтения `stdout`, `stderr` и операций записи в транспортный канал.

После обнаружения завершения оболочки он фиксирует количество байтов, уже находящихся в буфере каждого канала, используя Unix-механизм `FIONREAD`.

Эти данные, а также все ранее прочитанные байты должны быть сохранены, даже если принимающая сторона временно не может обрабатывать данные.

Среда выполнения Python на удалённом сервере должна поддерживать:

- `fcntl`.
- `termios.FIONREAD`.
- Опрос состояния Unix-каналов (`polling`).

Для обработки оставшегося вывода действуют два независимых ограничения.

**1. Ограничение на приём дополнительного вывода дочерних процессов**

Приём нового вывода дочерних процессов прекращается через одну секунду после обнаружения завершения основной оболочки.

Когда этот срок наступает, канал закрывается, если в нём больше нет байтов, зафиксированных при завершении оболочки.

Если зафиксированные байты ещё не были прочитаны, они продолжают считываться с учётом обратного давления (`backpressure`). После их извлечения канал закрывается.

Заключительная неблокирующая проба чтения одного байта позволяет отличить достижение конца потока (`EOF`) от ситуации, когда какой-либо дочерний процесс по-прежнему удерживает канал открытым.

Если проба получает байт, он также сохраняется.

Отбрасываться могут только дополнительные байты, поступившие от дочерних процессов после установленной границы.

Если в момент завершения приёма канал всё ещё открыт на запись, устанавливается `output_incomplete: true`.

Клиент отображает предупреждение и отмечает сохранённый вывод как неполный, но при этом сохраняет подтверждённый код завершения оболочки.

**2. Передача уже сохранённого вывода**

Для передачи сохранённых данных и последующего сообщения `result` не устанавливается отдельное ограничение в одну секунду.

Передача может продолжаться дольше окна приёма дополнительных данных.

Однако продолжают действовать:

- Общий тайм-аут выполнения.
- Отмена задания.
- Время жизни SSH-подключения.

Поэтому передача может завершиться ошибкой до получения подтверждения результата.

Само по себе медленное чтение данных принимающей стороной никогда не является причиной усечения вывода.

Цикл обработки событий проверяет сроки завершения с интервалом не более 50 мс между неблокирующими операциями с учётом планирования задач операционной системой.

Это не гарантирует, что обработчик завершится или клиент получит результат в течение одной секунды.

Закрытие канала может привести к отправке сигнала `SIGPIPE` дочернему процессу, который продолжает запись.

Отмена пользователем и ограничения размера журналов приложения остаются отдельными причинами неполного вывода.

Если процесс должен продолжать работу после завершения шага, его необходимо отделить от текущего процесса и перенаправить все три стандартных потока.

Например:

```sh
nohup my-command </dev/null >my-command.log 2>&1 &
```

Для управляемых фоновых служб предпочтительнее использовать системный менеджер служб.

Успешное завершение оболочки не подтверждает, что фоновый процесс корректно запустился, продолжил работу или выполнил поставленную задачу.

## Вывод и файлы

Создание локальных процессов выполняется через фоновый пул с ограниченным количеством одновременно обслуживаемых операций.

Для чтения нативных потоков `stdout` и `stderr` используются очереди объёмом **256 КиБ на каждый канал**, а также один находящийся в обработке блок размером **32 КиБ**.

Графический интерфейс обрабатывает до **64 КиБ на канал за один цикл обработки**.

При заполнении очередей применяется обратное давление (`backpressure`) к нативным каналам, а не принудительное завершение корректно работающей команды.

Реальные ошибки каналов, отмена задания и превышение времени выполнения обрабатываются отдельно.

Исходный поток вывода не сохраняется предварительно во временный файл.

Для передачи данных по удалённому каналу используются:

- Неблокирующий вызов `os.write`.
- Отслеживание частично выполненных операций записи.
- Очередь закодированных, но ещё не отправленных кадров объёмом **256 КиБ**.

Один частично отправленный кадр может дополнительно удерживать до **24 КиБ** памяти под исходные данные, не считая обычных накладных расходов объектов.

Если свободного места в очереди недостаточно для кадра данных, чтение приостанавливается. После этого буферы каналов ядра создают обратное давление на процессы, выполняющие запись.

Зарезервированное пространство позволяет выполнять заключительные проверки каналов и передавать завершающие управляющие сообщения.

Уже прочитанные данные никогда не удаляются ради освобождения места под сообщение `result`.

Сообщение о результате передаётся только после всех сохранённых данных вывода.

Блокировка транспортного канала не блокирует:

- Отслеживание завершения оболочки.
- Проверку времени прекращения приёма дополнительного вывода.

Память, используемая буферами каналов ядра, включая ещё не прочитанные зафиксированные байты, не входит в объём очереди закодированных кадров.

Полный поток направляется в журнал до достижения независимых ограничений хранилища.

Предварительный просмотр в графическом интерфейсе может пропускать записи или сокращать отображаемый текст. Такие изменения обозначаются явно.

Если запись журнала остановлена, соответствующая история выполнения отмечается как неполная.

Для каждого канонического каталога истории допускается только один процесс-владелец. Исключительный доступ обеспечивается блокировкой на уровне операционной системы.

### Обслуживание SQLite

Проверки истории в состоянии простоя не изменяют базу данных SQLite.

Процедура очистки удаляет устаревшие задания и проверяет фактически занятый объём дискового пространства после усечения WAL-файла.

Свободные страницы базы данных возвращаются файловой системе:

- При превышении бюджета хранилища.
- Либо когда объём свободных страниц составляет не менее **8 МиБ** и одновременно не менее **25%** базы данных.

Небольшие удаления оставляют свободные страницы для последующего повторного использования.

Новые базы данных используют механизм `incremental vacuum`.

Для существующих баз данных старого формата при первом возникновении необходимости в уплотнении выполняется один полный `VACUUM`, если доступного дискового пространства достаточно.

Последующее освобождение страниц выполняется пакетами не более **256 страниц** с контрольными точками WAL.

При удалении истории из-за превышения бюджета учитываются страницы, которые могут быть освобождены.

Когда накопленного объёма таких страниц достаточно для соблюдения лимита, выполняется освобождение пространства, после чего проверяется фактический размер данных на диске.

Только после этой проверки принимается решение о необходимости дальнейшего удаления истории.

### Завершение приложения

При закрытии окна приложение запрашивает отмену операций обслуживания и прерывает активное уплотнение SQLite, не блокируя поток графического интерфейса.

Блокировка каталога истории сохраняется до закрытия соединения с базой данных в фоновом рабочем потоке.

Отмена проверяется между операциями удаления записей и пакетами уплотнения.

Операцию файловой системы, которая уже выполняется, невозможно гарантированно прервать немедленно.

### Ограничения передачи и выполнения файлов

Выполнение больших локальных скриптов пока не реализовано.

Предусмотренный для будущей реализации механизм использует отдельный поток или файловый дескриптор, создаваемый после перехода через sudo.

Он не предполагает использования общего временного скрипта или ослабления прав доступа к каталогам.

Передача отдельных файлов через SFTP использует независимую подготовительную область (`staging`) и проверки перед перезаписью существующих файлов.
