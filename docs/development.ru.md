# Разработка

**Русский** | [English](development.md)

---

Для разработки требуется Python версии **3.12 или новее** и отдельное виртуальное окружение.

Из корневого каталога репозитория выполните:

```sh
python -m pip install -r requirements-dev-lock.txt
python -m pip install --no-deps --no-build-isolation -e .
python tools/check_repo.py
python -m pytest -q
```

Тестирование использует локальные подпроцессы и синтетические хосты.

Для запуска тестов графического интерфейса без дисплея установите переменную окружения:

```sh
QT_QPA_PLATFORM=offscreen
```

Переменная `NODEBATCH_TEST_LOOPBACK=1` включает интеграционное тестирование реальных системных SSH/SFTP-клиентов с использованием временного SSH-сервера на `127.0.0.1`.

Интеграционные тесты Windows/WSL дополнительно требуют следующие переменные окружения:

- `NODEBATCH_TEST_WSL_HELPER`
- `NODEBATCH_TEST_WSL_DISTRO`
- `NODEBATCH_TEST_WSL_REPO`
- `NODEBATCH_TEST_WSL_PYTHON`

Они должны указывать на локальный вспомогательный обработчик и тестовую среду.

Интеграционные тесты не используют рабочие удалённые серверы пользователя.

## Языки и исходный код

Идентификаторы Python, комментарии, docstring и исходные сообщения должны оставаться на английском языке.

Для локализации текста приложения используйте функцию:

```python
tr("English message", ...)
```

Русский перевод необходимо добавлять в файл:

```text
src/nodebatch/locales/ru.json
```

При переводе необходимо сохранять:

- Плейсхолдеры форматирования.
- Имена и синтаксис команд.
- Данные, введённые пользователем.

Кнопки Qt переводятся отдельно.

В исходном коде и документации используйте обычный дефис `-`, а не типографские длинные тире.

## Какие файлы должны находиться в Git

В репозитории должны храниться:

- Исходный код приложения.
- Синтетические тесты.
- Пустые конфигурации по умолчанию.
- Публичная документация.
- Конфигурации CI.

В репозиторий не должны попадать:

- Пользовательские YAML-конфигурации.
- Приватные SSH-ключи.
- Файлы `known_hosts`.
- История выполнения команд.
- Журналы.
- Виртуальные окружения.
- Скриншоты.
- Отчёты о конкретных машинах.
- Скомпилированные исполняемые файлы.

Файл `.gitignore` в корне репозитория использует список разрешённых путей (`allowlist`). Это предотвращает случайное добавление неожиданных файлов в корневой каталог.

Новые публичные файлы в корне репозитория необходимо явно добавлять в список разрешённых.

Скрипт `check_repo.py` дополнительно проверяет файлы, которые могут попасть в Git, включая уже отслеживаемые файлы, скрыть которые с помощью `.gitignore` невозможно.

При обнаружении потенциально опасных данных скрипт выводит только пути к файлам, но не содержимое найденных секретов.

### Локальные рабочие файлы

Для локальной работы используйте каталог:

```text
.local/
```

Он исключён из:

- Git.
- Python wheel-пакетов.
- Архивов исходного кода.
- Сборок приложения.

Исторические заметки по ревью и отчёты о конкретных машинах, если они существуют, должны храниться в:

```text
.local/reports/
```

Для тестовых данных, создаваемых во время выполнения, следует использовать временные каталоги.

## Сборка приложения

Сборка выполняется отдельно для Linux и Windows. Кросс-компиляция не предусмотрена.

```sh
python tools/build.py
python tools/verify_bundle.py dist/linux/NodeBatch
# Windows: python tools/verify_bundle.py dist/windows/NodeBatch
```

Распространять необходимо весь каталог `NodeBatch`, включая вспомогательный обработчик и библиотеки среды выполнения.

Параметр `--dist-root` позволяет создавать отдельную проверочную сборку, не заменяя содержимое существующего каталога `dist`.

Файл `pyproject.toml` явно перечисляет ресурсы, включаемые в пакет.

При сборке копируются только объявленные ресурсы и публичные документы, перечисленные в:

```text
tools/release_files.py
```

Сборка никогда не копирует целиком рабочий каталог документации или пользовательской конфигурации.

Профили и inventory, включаемые в дистрибутив, должны оставаться пустыми и универсальными.

### Непрерывная интеграция

CI выполняет:

- Проверку чистоты и корректности содержимого репозитория.
- Автоматические тесты.
- Сборку приложения.
- Проверку готовых пакетов для обеих платформ.

Успешное локальное выполнение тестов не является доказательством успешного завершения облачного CI.

Каждая сборка использует новый промежуточный каталог (`staging`).

Предыдущий каталог результата перемещается в `.previous-*`, а не объединяется с новым. Это предотвращает попадание устаревших файлов в новую сборку приложения.

CI загружает в артефакты исключительно каталог `NodeBatch` соответствующей платформы.

### Лицензирование и публикация

Проект распространяется по лицензии MIT.

Сборка также включает:

```text
THIRD_PARTY.md
licenses/
```

Эти файлы содержат информацию о сторонних библиотеках и их лицензиях. Они должны распространяться вместе с готовыми бинарными файлами.

CI публикует сборочные артефакты для проверки.

Загрузка артефактов в GitHub Actions сама по себе не создаёт GitHub Release.

## Первая публикация

Корневым каталогом репозитория должен оставаться каталог, содержащий:

```text
pyproject.toml
.github/
```

Создайте пустой удалённый репозиторий, затем подключите его и отправьте подготовленную ветку `main`:

```sh
git remote add origin REPOSITORY_URL
git push -u origin main
```

Замените `REPOSITORY_URL` фактическим адресом удалённого репозитория.

Каталоги с бинарными файлами и локальные отчёты должны оставаться вне Git.

Готовые сборки приложения следует публиковать отдельно как файлы релиза (`release assets`).

## Локальные измерения производительности

Для проведения локальных измерений используйте:

```sh
python tools/benchmark_output.py --output .local/reports/benchmark.json
python tools/preview.py .local/previews
```

Нагрузочный инструмент формирует поток данных со скоростью **5 МиБ/с в течение 60 секунд** при уровнях параллелизма:

- 1.
- 4.
- 100.

В тестах используются длинные, короткие и UTF-8 сообщения.

Инструмент измеряет:

- Фактическую пропускную способность.
- Задержку обработки событий.
- Поведение при отмене заданий.
- RSS-память графического интерфейса.
- Объём сохранённых данных.

Процессы-генераторы нагрузки и файловый кеш операционной системы не входят в измеряемую RSS-память графического интерфейса.

Результаты тестирования в режиме `offscreen` не заменяют:

- Проверки с настоящим графическим окном.
- Измерения памяти полного дерева процессов.
- Проверки реальных политик sudo.
- Тестирования на настоящих BSD-системах.

Результаты измерений следует сохранять локально, а не добавлять в репозиторий или релизный пакет как универсальные характеристики производительности.
