# Конфигурация

**Русский** | [English](configuration.md)

---

При первом запуске приложение создаёт YAML-файлы конфигурации, принадлежащие пользователю. Конфигурации, включённые в дистрибутив, используются исключительно как шаблоны и никогда не содержат реальных серверов, учётных данных или приватных путей.

Файл `settings.yaml` содержит профили подключений, ограничения выполнения команд и параметры журналирования.

Версия схемы конфигурации остаётся `1`. Параметр `language` принимает значения `auto`, `en` или `ru`. Если параметр отсутствует, используется `auto`.

Для применения изменения языка необходимо перезапустить приложение. Остальные корректные изменения конфигурации применяются к последующим заданиям. Если конфигурационный файл содержит ошибки, приложение продолжает использовать последнюю успешно загруженную конфигурацию.

```yaml
version: 1
language: en
```

Не заменяйте весь файл `settings.yaml` приведённым фрагментом. Изменяйте соответствующий параметр в уже созданном файле.

Профили позволяют выбирать способ подключения (`native` или `wsl`), а также необязательные пути к SSH-конфигурации, ключам и файлам `known_hosts`.

При использовании WSL необходимо явно указать установленный дистрибутив. Пути внутри WSL должны использовать синтаксис Unix.

Файл `inventory.yaml` позволяет добавлять метаданные серверов и хосты, отсутствующие в SSH-конфигурации.

Пример содержит условные имена серверов и адреса, предназначенные исключительно для документации:

```yaml
version: 1
hosts:
  - alias: example-node
    address: 192.0.2.10
    user: operator
    os: linux
    shell: sh
    tags: [example]
groups:
  example: [example-node]
```

Сценарии следует размещать в каталоге `scenarios/` внутри пользовательского каталога конфигурации.

Пример сценария:

```yaml
id: system-check
name: System check
os: [unix]
shells: [sh, bash]
parameters: {}
steps:
  - name: Show system
    command: |
      uname -a
      id
```

Каждый шаг сценария создаёт отдельное SSH-подключение.

Поля `sudo: true`, `sudo_user` и `timeout` являются необязательными.

Параметры шаблона вида `{{name}}` должны использоваться как отдельные аргументы командной строки, без кавычек.

В блоках команд, использующих шаблонные параметры, запрещены:

- Heredoc-конструкции.
- Подстановка команд.
- Конструкции `${}`.
- Обратные кавычки (backticks).

Блоки команд без шаблонных параметров могут содержать обычные многострочные shell- и Python-heredoc-конструкции.

Размер сформированной команды не должен превышать **32 768 байт в UTF-8**.

## Правила безопасности

Файл `safety.yaml` определяет правила трёх типов:

- `allow` - разрешить выполнение.
- `confirm` - запросить подтверждение.
- `deny` - запретить выполнение.

Правила `deny` имеют наивысший приоритет.

Эти правила помогают предотвращать распространённые ошибки, но не гарантируют безопасность произвольного выполняемого кода.

SSH-конфигурация считается доверенной, включая локальные команды, которые OpenSSH может выполнять на её основании.

## Хранение данных и журналирование

Для ограничения использования дискового пространства применяются параметры:

- `logging.run_max_bytes` - максимальный размер журнала одного задания.
- `logging.history_max_bytes` - общий бюджет каталога истории.
- `logging.min_free_bytes` - минимальный резерв свободного дискового пространства.

Устаревший параметр `max_bytes` продолжает использоваться как резервное значение, если отсутствуют новые ограничения размера отдельных журналов или истории.

В общий бюджет хранения включаются:

- База данных SQLite.
- Файлы SQLite WAL/SHM.
- Журналы выполнения заданий.

Транзакции изменения статусов и операции обслуживания SQLite могут временно превышать установленный бюджет.

Активные журналы никогда не удаляются.

Проверки истории в состоянии простоя не выполняют запись в базу данных.

Очистка удаляет устаревшие задания и постепенно освобождает неиспользуемые страницы базы данных при нехватке дискового пространства или накоплении значительного объёма свободных страниц.

При удалении записей из-за превышения лимита учитываются страницы, доступные для повторного использования. После освобождения места проверяется фактический размер занимаемого дискового пространства.

Рост WAL-файла сам по себе не является основанием для дополнительного удаления истории.

Старые базы данных проходят однократную миграцию при возникновении необходимости в уплотнении.

Фактическая очистка выполняется в фоновом режиме. Пока она не завершится, подготовка новых заданий блокируется.

Подробнее о пороговых значениях, механизмах освобождения дискового пространства и отмене операций см. [Выполнение команд, секреты и результаты](execution.ru.md#вывод-и-файлы).
