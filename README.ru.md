# NodeBatch

**Русский** | [English](README.md)

---

NodeBatch запускает команды и сценарии на нескольких SSH-хостах из одного окна.
Вы выбираете серверы или группу, проверяете задание и получаете отдельный результат
для каждого хоста. Есть последовательное и параллельное выполнение, sudo, история
и передача отдельных файлов через SFTP.

Это приложение для пакетных операций. Для интерактивной работы с сервером нужен
обычный SSH-терминал.

## Принцип работы

NodeBatch использует системные `ssh` и `sftp`. Соединениями, ключами, SSH-agent и
ProxyJump управляет OpenSSH; приложение собирает задание и показывает его ход.

1. Читает активный профиль из `settings.yaml`.
2. Собирает хосты из SSH-конфига и `inventory.yaml`, добавляет группы и метки.
3. Перед запуском показывает выбранные хосты, команды, sudo и замечания правил безопасности.
4. Для каждого хоста разрешает SSH-настройки через `ssh -G` и проверяет ОС через `uname -s`.
5. Отправляет команду удалённому Python-обработчику. Обработчик запускает `sh` или `bash`,
   передаёт вывод и подтверждённый код завершения оболочки.
6. Сохраняет результаты в SQLite, а вывод задания в JSONL-журнал.

В последовательном режиме хосты обрабатываются по очереди. В параллельном режиме
одновременно работают несколько хостов, но шаги одного сценария на каждом хосте
всё равно идут последовательно. Одно окно выполняет одно задание за раз.

Каждый шаг создаёт отдельное подключение и новую оболочку. `cd`, переменные и
активация окружения не сохраняются между шагами. Зависимые действия объединяйте
в один shell-блок.

## Установка и запуск

### Требования

| Где | Что нужно |
|---|---|
| Компьютер с готовой сборкой | Windows или Linux, системные `ssh` и `sftp` |
| Запуск из исходников | Дополнительно Python 3.12+ и зависимости проекта |
| Удалённый хост | Unix, доступ по SSH, `sh` или `bash`, команда `python3` |
| Удалённый обработчик | Python с `fcntl`, `termios.FIONREAD` и поддержкой polling для Unix-pipe |
| Windows с backend `wsl` | Установленный и настроенный WSL-дистрибутив с OpenSSH внутри него |

Типы Linux, FreeBSD, OpenBSD, NetBSD и macOS предусмотрены в inventory. Это не
означает, что все системы прошли реальную приёмку: особенности shell и команды
ваших сценариев нужно проверять на целевой ОС. Windows-серверы как удалённые
PowerShell/cmd-хосты не поддерживаются.

### Готовая сборка

Распакуйте всю папку `NodeBatch`. Сохраните `_internal`, `nodebatch-askpass`,
документацию и лицензии рядом с приложением.

- Windows: запустите `NodeBatch.exe` с локального диска.
- Linux: запустите `./NodeBatch` из распакованной папки.

Для готовой сборки устанавливать Python на свой компьютер не нужно. На удалённых
хостах `python3` всё равно нужен. Бинарник Linux следует проверять на своей версии
дистрибутива: совместимость со старыми glibc не следует из названия Linux-сборки.

### Исходники

Из корня проекта создайте виртуальное окружение:

```sh
python -m venv .venv
```

Активируйте его:

```sh
# Linux
. .venv/bin/activate
```

```powershell
# Windows PowerShell
.\.venv\Scripts\Activate.ps1
```

Установите зависимости и сам проект:

```sh
python -m pip install -r requirements-lock.txt
python -m pip install --no-deps --no-build-isolation -e .
nodebatch
```

Можно использовать `python -m nodebatch`. Для паролей и подтверждения ключей нужен
`nodebatch-askpass`, поэтому установка проекта обязательна, одного `PYTHONPATH` мало.

## Первая настройка

1. Откройте `Настройки`, посмотрите путь к каталогу конфигурации.
2. В разделе `Подключения` выберите backend, программы SSH/SFTP и SSH-конфиг.
3. Нажмите `Найти в системе / проверить`, выберите найденные программы и нужные ключи.
4. Проверьте, какой профиль выбран как активный, и сохраните настройки.
5. Добавьте хосты в SSH-конфиг или в `Источники хостов`.
6. Обновите список хостов. Сначала отметьте один сервер и выполните `uname -a` и `id`.
7. После успешной проверки создайте группы и настройте параллельность, таймауты и журнал.

Проверка окружения ищет локальные программы и файлы. Она не подтверждает доступность
сервера, правильность пароля или права sudo. При нехватке зависимостей можно открыть
системный установщик отдельной кнопкой. Перед этим приложение показывает команду из
`dependencies.yaml`; на удалённых серверах оно ничего автоматически не устанавливает.

## Конфиги и SSH-ключи

### Где лежат файлы

При первом запуске NodeBatch создаёт пользовательские YAML и пример `system-info`.
Файлы из `src/nodebatch/defaults` являются шаблонами: рабочие настройки меняйте в
каталоге, который указан в интерфейсе.

| Данные | Linux | Windows |
|---|---|---|
| Конфигурация | `~/.config/nodebatch` | `%APPDATA%\NodeBatch` |
| История и журналы | `~/.local/state/nodebatch` | `%LOCALAPPDATA%\NodeBatch` |

На Linux учитываются `XDG_CONFIG_HOME` и `XDG_STATE_HOME`. Для отдельных окружений
можно указать свои каталоги:

```sh
nodebatch --config-dir ./operator-config --data-dir ./operator-state
```

Это пути на вашем компьютере. В Windows история SQLite, приложение и файлы для
передачи через WSL должны находиться на локальном диске, а не в UNC-каталоге.

| Файл | Назначение |
|---|---|
| `settings.yaml` | Профили, активное подключение, выполнение, язык и лимиты хранения |
| `inventory.yaml` | Дополнительные хосты, ОС, shell, группы и метки |
| `safety.yaml` | Правила `allow`, `confirm`, `deny` для команд и путей назначения |
| `dependencies.yaml` | Команды локальной установки OpenSSH и WSL |
| `scenarios/*.yaml` | Многошаговые сценарии и их параметры |
| SSH `config` | HostName, User, Port, IdentityFile, ProxyJump и другие параметры OpenSSH |
| SSH `known_hosts` | Ключи уже известных серверов |

### `settings.yaml`

Полный пример с исходными лимитами:

```yaml
version: 1
language: auto
active_profile: native
profiles:
  native:
    backend: native
    ssh: ssh
    sftp: sftp
    config: ''
    keys: []
    known_hosts: ''
    wsl_distribution: ''
    wsl_home: ''
execution:
  mode: sequential
  parallelism: 4
  stop_on_error: true
  connect_timeout: 10
  step_timeout: 600
  auth_timeout: 120
  sudo_user: root
logging:
  retention_days: 30
  max_bytes: 1073741824
  run_max_bytes: 268435456
  history_max_bytes: 1073741824
  min_free_bytes: 16777216
  gui_blocks: 2000
  verbose: false
watch:
  debounce_ms: 500
  poll_ms: 2000
```

| Параметр | Как работает |
|---|---|
| `active_profile` | Профиль, который используют новые задания |
| `backend: native` | SSH/SFTP запускаются непосредственно в вашей ОС |
| `config: ''` | OpenSSH использует обычные настройки; каталог хостов ищет `~/.ssh/config` |
| `known_hosts: ''` | Используются стандартные файлы OpenSSH |
| `keys: []` | Нет дополнительных `-i`; остаются настройки OpenSSH и агент |
| `parallelism` | От 1 до 100 одновременных хостов, действует в режиме `parallel` |
| `stop_on_error` | После ошибки не начинать новые хосты и следующие шаги; уже работающие операции продолжаются |
| `connect_timeout` | Таймаут установления SSH-соединения, секунды |
| `auth_timeout` | Ожидание авторизации, секунды |
| `step_timeout` | Таймаут шага, включая передачу запроса и доставку результата после `ready` |
| `sudo_user` | Начальное значение пользователя sudo для свободной команды |
| `retention_days` | Срок хранения завершённых заданий |
| `run_max_bytes` | Максимальный размер журнала одного задания, в байтах |
| `history_max_bytes` | Бюджет всего каталога истории, включая SQLite и WAL/SHM |
| `min_free_bytes` | Минимальный резерв свободного места на диске |
| `gui_blocks` | Лимит отображения вывода; самостоятельная запись журнала имеет свои лимиты |
| `max_bytes` | Совместимое старое поле, резерв для отсутствующих run/history-лимитов |
| `watch` | Задержка перечитывания и период проверки изменений, миллисекунды |

В GUI размеры хранения задаются в МиБ, в YAML сохраняются в байтах.
Редактируемый профиль и активный профиль - разные поля: изменение профиля не
включает его автоматически. Выберите `Активный профиль` и нажмите `Сохранить настройки`.

Большинство сохранённых изменений применяется к следующим заданиям. Уже созданное
задание использует свой снимок параметров. При некорректном YAML приложение сохраняет
последнюю загруженную корректную конфигурацию; ошибку в файле нужно исправить до
нового запуска. Если файл изменили извне во время редактирования формы, сначала
нажмите `Перечитать файлы` и перенесите свои несохранённые изменения.

### Как включить нужные ключи

NodeBatch не хранит содержимое приватных ключей в YAML. В профиле указываются пути
к уже существующим файлам. Выбирайте приватный ключ, не его публичную часть `.pub`.

1. Откройте `Настройки > Подключения`, выберите редактируемый профиль.
2. Нажмите `Добавить ключ` и укажите файл, либо выберите его в `Найденные ключи`
   и нажмите `Добавить найденный ключ`.
3. Убедитесь, что путь появился в поле `IdentityFile`: один путь на строку.
4. Сделайте этот профиль активным и сохраните настройки.

Соответствующий фрагмент профиля в YAML:

```yaml
keys:
  - ~/.ssh/id_ed25519_ops
  - ~/.ssh/id_ed25519_backup
```

Каждый путь становится дополнительным аргументом `ssh -i` и `sftp -i`. Эти ключи
применяются ко всем хостам активного профиля. Чтобы убрать дополнительный ключ,
удалите его строку и сохраните. Отдельных переключателей `enabled` или флажков
включения у ключей сейчас нет. Нахождение ключа диагностикой само по себе его не включает.

Удаление строки не запрещает OpenSSH использовать тот же ключ из `IdentityFile`
в SSH-конфиге или через агент. Для отдельных ключей на разные серверы удобнее оставить
`keys: []` и описать их в SSH-конфиге:

```sshconfig
Host web-01
    HostName 192.0.2.10
    User operator
    Port 22
    IdentityFile ~/.ssh/id_ed25519_web
    IdentitiesOnly yes

Host db-01
    HostName 192.0.2.20
    User operator
    IdentityFile ~/.ssh/id_ed25519_db
    IdentitiesOnly yes
```

Адреса здесь учебные, замените их своими. `IdentitiesOnly yes` ограничивает выбор
ключами, настроенными для подключения; если в конфиге несколько `IdentityFile`,
они всё ещё учитываются. Один `keys: []` не отключает агент и парольный вход.

Ключ создаётся вне NodeBatch, например `ssh-keygen -t ed25519`. Публичная часть
должна быть добавлена на сервер в `authorized_keys`, приватная остаётся локально.
Если у приватного ключа есть парольная фраза, приложение запросит её при необходимости.
Пароли и фразы не записываются в YAML. Не добавляйте свои ключи в репозиторий.

На Windows для native можно использовать пути вида `C:/Keys/id_ed25519_ops`.
Для WSL нужны пути внутри выбранного Linux-дистрибутива, например
`~/.ssh/id_ed25519_ops`. Нативный и WSL-агенты являются разными окружениями.

### Профиль WSL

На Windows проверьте названия установленных дистрибутивов:

```powershell
wsl --list --quiet
```

Добавьте в `profiles` такой профиль и выберите его через `active_profile` или GUI.
`Debian` здесь пример; имя должно совпадать с установленным дистрибутивом.

```yaml
wsl:
  backend: wsl
  ssh: ssh
  sftp: sftp
  config: ~/.ssh/config
  keys: []
  known_hosts: ''
  wsl_distribution: Debian
  wsl_home: ''
```

`wsl_home: ''` позволяет определить HOME автоматически. Конфиг, ключи и known_hosts
читаются в WSL, с Unix-путями. Сам NodeBatch, его Windows-helper и локальные файлы
для передачи должны находиться на локальном Windows-диске. Не переносите native-пути
в WSL-профиль без преобразования. Новый дистрибутив сначала нужно открыть и завершить
его обычную первичную настройку.

### Хосты и `inventory.yaml`

Для списка хостов нужны конкретные алиасы `Host web-01`. Шаблон `Host *.example`
не разворачивается в набор серверов. Include-файлы учитываются; окончательные
параметры подключения всё равно разрешает OpenSSH.

Inventory может добавить новые хосты или дополнить алиасы SSH-конфига:

```yaml
version: 1
hosts:
  - alias: web-01
    address: 192.0.2.10
    user: operator
    port: 22
    os: linux
    shell: sh
    tags: [web, production]
  - alias: db-01
    os: linux
    shell: bash
    tags: [database]
groups:
  web: [web-01]
  maintenance: [web-01, db-01]
```

`db-01` в этом примере получает адрес и пользователя из SSH-конфига. Непустые
`address`, `user` и заданный `port` из inventory передаются OpenSSH как явные
параметры и имеют приоритет. При одинаковом алиасе получается один хост.

`os: unix` означает отсутствие конкретного ожидания ОС; `os: linux` или `freebsd`
проверяются по фактическому `uname -s`. `shell` принимает только `sh` и `bash`.
Метки помогают поиску, но не заменяют группы. Ключи отдельного хоста задавайте
через SSH-конфиг: поля `keys` у строки inventory нет.

## Создание групп

1. На вкладке `Хосты и команды` отметьте нужные серверы.
2. Нажмите `Создать группу`, задайте имя. Отмеченные серверы попадут в новую группу.
3. Проверьте состав в правой части диалога и нажмите `Сохранить`.
4. Для изменения состава используйте `Управление группами`: доступны добавление,
   исключение участников, переименование и удаление группы.

Группы записываются в `inventory.yaml`, в раздел `groups`, как в примере выше.
Можно включить алиас из SSH-конфига, не создавая отдельную строку в `hosts`.
Один сервер может состоять в нескольких группах. Удаление группы не удаляет серверы
и не меняет SSH-конфиг. Общий inventory используется профилями приложения; участник,
которого нет в текущем профиле, сохраняется в группе.

Выбор группы в основном окне отмечает её участников и снимает остальные отметки.
Поиск только скрывает строки: скрытый отмеченный хост остаётся в задании.
`Выбрать видимые` добавляет видимые хосты к отметкам. Перед новым выбором удобно
нажать `Снять все`; окончательный состав всегда проверяйте в окне запуска.

## Запуск команд и сценариев

### Свободная команда

1. Выберите группу или отметьте хосты вручную.
2. Выберите свободную команду и оставьте режим `Пользователь SSH` для обычного запуска.
3. Введите, например:

```sh
uname -a
id
df -h
```

4. Нажмите `Проверить и запустить`. Проверьте серверы, команды и предупреждения.
5. Подтвердите задание. При первом соединении проверьте fingerprint сервера по
   независимому доверенному источнику. Затем ответьте на запросы авторизации.
6. Следите за результатами по хостам. Полный доступный журнал находится в `История`;
   вывод можно экспортировать.

Сначала проверьте операцию на одном сервере. Автоматического отката нет.
При изменении SSH-файлов после проверки приложение может приостановить задание
и потребовать повторного просмотра настроек.

### Сценарий

Создайте файл `scenarios/inspect-directory.yaml` в своём каталоге конфигурации
или используйте `Настройки > Сценарии > Новый сценарий`:

```yaml
id: inspect-directory
name: Inspect directory
description: Show the current user and inspect a directory.
os: [linux]
shells: [sh, bash]
parameters:
  directory:
    required: true
    default: /var/log
steps:
  - name: Show system and user
    command: |
      uname -a
      id
  - name: Inspect directory
    command: ls -ld -- {{directory}}
    timeout: 30
```

Сохраните сценарий отдельной кнопкой `Сохранить сценарий`, выберите его на основной
вкладке и заполните параметры. `Сохранить настройки` не заменяет сохранение сценария.
При выборе сценария используются его шаги и поля sudo, а не режим свободной команды.

`{{directory}}` должен быть отдельным словом без кавычек. NodeBatch сам экранирует
значение для shell. Конструкции `"{{directory}}"` и `prefix{{directory}}` запрещены.
Блок с подстановками нельзя совмещать с heredoc, `$()`, `${}` и обратными кавычками.
В блоке без шаблонов можно использовать обычный многострочный shell или Python heredoc.

Секретные параметры объявляются как `secret: true` и привязываются к шагу через
`secrets: [parameter_name]`. Подстановка секретов через `{{...}}` запрещена: шаг
читает значение из дескриптора `NODEBATCH_SECRET_<name>_FD`. Ограничение - 32 секрета
на шаг, по 4096 байт UTF-8. Готовый пример есть в [описании выполнения](docs/execution.md#secrets).

### Sudo

Для свободной команды выберите sudo и укажите целевого пользователя. В сценарии
используйте поля шага `sudo: true` и `sudo_user: root` или другое имя пользователя.
SSH-вход остаётся от пользователя подключения; sudo определяет пользователя команды.

Фактически sudo запускает `python3 -u -c ...`, а Python создаёт выбранную оболочку.
Разрешения sudoers только на `sh` или `bash` для этого недостаточно. Разрешение этого
обработчика означает возможность выполнять произвольный код от целевого пользователя.
NodeBatch не редактирует sudoers; `requiretty` и произвольные PAM-диалоги не поддерживаются
как общий случай. Передача файлов через SFTP использует SSH-пользователя, без sudo.

### Передача файлов

На вкладке `Файлы` выберите направление, хосты, локальный и удалённый пути.
Выбор хостов общий с вкладкой команд. Передаётся один файл за задание.

- Отправка: выберите локальный файл и полный удалённый путь, включая имя файла.
- Получение: выберите локальный каталог и удалённый файл. Результат сохраняется
  в подкаталоге с алиасом хоста, чтобы одноимённые файлы разных серверов не смешивались.
- Замена существующего файла требует отдельного подтверждения. При отказе существующий
  файл сохраняется, операция для этого хоста считается неуспешной.

Передача каталогов, рекурсивная синхронизация и SFTP через sudo не реализованы.

## ROADMAP настроек

Маршрут настройки текущей версии:

| Этап | Раздел | Что проверить |
|---|---|---|
| 1 | Подключения | native/WSL, программы, SSH-конфиг, known_hosts |
| 2 | Подключения / IdentityFile | Пути ключей, активный профиль, подходящий агент |
| 3 | Источники хостов и группы | Алиасы, ожидаемая ОС, shell, состав групп |
| 4 | Выполнение | Последовательный тест, затем параллельность, остановка очереди, таймауты |
| 5 | Безопасность | Правила и подтверждения для ваших операций |
| 6 | Логи и хранение | Срок хранения, бюджет каталога, лимит задания и резерв диска |
| 7 | Сценарии | Проверка на одном хосте, затем запуск на группе |

Предложения для дальнейшего развития настроек, без обещанных сроков:

- [ ] Отдельные флажки включения ключей и сводка эффективных IdentityFile/агента до запуска.
- [ ] Формы добавления и редактирования хостов вместо обязательного редактирования YAML.
- [ ] Клонирование и экспорт профилей с явным исключением локальных путей и секретов.
- [ ] Версионирование настроек, резервные копии и восстановление выбранной версии через GUI.

Эти пункты пока не реализованы. Большие локальные скрипты и дополнительные платформенные
проверки являются отдельными задачами, а не доступными переключателями настроек.

## Нюансы и ограничения

### Результат, отмена и фоновые процессы

Подтверждённый код относится к основной оболочке. Ошибка до запуска команды отличается
от неизвестного результата после передачи запроса. Код `255` может быть подтверждённым
кодом команды, поэтому не всякий `255` означает ошибку SSH.

Отмена закрывает соединение, но не доказывает остановку удалённой команды или её потомков.
При потере подтверждения результат остаётся неизвестным. Автоматических повторов нет:
повторяйте изменяющую операцию только после проверки состояния сервера.

После выхода оболочки новые данные потомков принимаются ещё секунду. Уже полученный
вывод и байты, находившиеся в pipe при обнаружении выхода, сохраняются при медленной
доставке. Доставка данных и результата может занять дольше секунды и входит в таймаут
шага. Возможное обрезание помечается `output_incomplete`; это не меняет подтверждённый
код оболочки. Фоновым сервисам нужны отсоединение и перенаправление всех потоков,
например `nohup my-command </dev/null >my-command.log 2>&1 &`, либо менеджер служб.

### Вывод, история и безопасность

- Одна команда ограничена 32 КиБ UTF-8 после подстановок. Исполнение большого локального
  файла скрипта пока не реализовано. Деление на шаги подходит только независимым блокам.
- stdin SSH-соединения занят протоколом; программа получает `/dev/null`.
  Интерактивные приложения, TTY, ввод ответов через терминал не поддерживаются.
- Очереди вывода ограничены; медленный клиент создаёт обратное давление. GUI может
  сокращать отображение, а журнал независимо ограничивается настройками хранения.
- При достижении лимита запись вывода прекращается с явной отметкой неполного журнала.
  Активные задания очистка не удаляет. Обслуживание истории выполняется в простое;
  во время фактического обслуживания подготовка нового задания может быть отклонена.
- Один каталог истории может использовать только один экземпляр приложения. Второму
  экземпляру нужен другой `--data-dir`. В Windows нельзя использовать UNC для SQLite.
- Правила безопасности проверяют текст и распространённые ошибки, но не доказывают
  безопасность произвольного скрипта. SSH-конфиг доверенный: ProxyCommand и Match exec
  могут запускать локальные программы, в том числе при разрешении настроек.
- Известные точные значения секретов маскируются, но их преобразования, например base64,
  автоматически не распознаются. Код, получивший секрет через FD, тоже должен его беречь.
- Язык пользовательских сценариев, имён хостов и удалённого вывода не переводится.

### Язык и применение настроек

Русский и английский выбираются в настройках с перезапуском приложения:

```sh
nodebatch --language ru
nodebatch --language en
```

Приоритет: `--language`, затем `settings.yaml: language`. Значение `auto` использует
`NODEBATCH_LANG=ru|en`, если переменная задана, иначе язык системы.
При переходе со старой версии каталоги не импортируются автоматически: закройте её,
перенесите нужные YAML вручную и обновите ссылки на секретные FD до `NODEBATCH_SECRET_<name>_FD`.

### Если что-то не работает

| Симптом | Что проверить |
|---|---|
| Нет серверов в списке | Активный профиль, путь config, конкретные Host-алиасы, синтаксис inventory, обновление списка |
| Ключ не используется | Файл приватный, путь относится к native/WSL, профиль сохранён и активен; проверьте IdentityFile и агент |
| `Permission denied` | Пользователя и права на ключ, public key на сервере, способы аутентификации OpenSSH |
| Не найден askpass | Установлен ли проект через pip либо сохранена ли вся папка готовой сборки |
| Нет `python3` или Bash на хосте | Установите нужную программу на сервере или выберите доступный shell |
| sudo не работает | Пользователя sudo, право запуска Python-обработчика, ограничения sudoers и TTY |
| Конфиг не сохраняется | Валидность YAML и внешние изменения; перечитайте файлы перед новой правкой |
| Новое задание не начинается | Завершение текущего задания или обслуживания, бюджет истории и свободное место |
| Результат неизвестен | Состояние сервера, связь и таймаут; не считайте это подтверждением неисполнения |

Локальную проверку YAML можно выполнить без SSH-подключений:

```sh
nodebatch --validate-config
```

Она не заменяет проверку доступности хостов и ключей. Если указанный каталог ещё
не инициализирован, команда сначала создаст в нём шаблоны конфигурации.

## Сборка и разработка

В активном виртуальном окружении:

```sh
python -m pip install -r requirements-dev-lock.txt
python -m pip install --no-deps --no-build-isolation -e .
python tools/check_repo.py
python -m pytest -q
python tools/build.py
python tools/verify_bundle.py
```

Сборка PyInstaller выполняется на каждой ОС отдельно. Результат находится в
`dist/windows/NodeBatch` или `dist/linux/NodeBatch`. Передавайте всю папку.
GitHub Actions выполняет проверки и загружает сборки как артефакты; это не создаёт
GitHub Release автоматически. Локальные YAML, история, ключи, отчёты и сборки в Git
не входят; рабочие примеры конфигурации из этого README не содержат настоящих серверов.

Подробнее: [формат конфигурации](docs/configuration.md),
[протокол, секреты и результат](docs/execution.md), [разработка](docs/development.md).
Код NodeBatch распространяется под [MIT](LICENSE); [лицензии библиотек](THIRD_PARTY.md)
сохраняются отдельно и включаются в готовую сборку.
